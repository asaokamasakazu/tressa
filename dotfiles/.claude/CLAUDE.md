# commitメッセージルール
下記のいずれかのプレフィックスを使用してください。
- 機能追加/機能修正：feat: ✨
- 機能以外の追加：add: ⚡️
- 機能以外の修正：change: 💫
- バグ修正：fix: 🐛
- 削除：remove: 🔥
- ソースコードのフォーマット調整（lint系）：style: 🎨
- ドキュメント更新：docs: 📚
- リファクタ：refactor: ♻️
- パフォーマンス改善：perf: 🦄
- ライブラリ：package: 📦
- テストコード：test: ✅
- CI：ci: 💚
- リバート：revert: ⏪️
- タスクファイルなどプロダクションに影響のない修正：chore: 🩹
- Work In Progress：wip: 🚧

## 例
fix: 🐛 **を修正
test: ✅ Foo Bar のテストケースを追加

## 注意点
「style」はCSSの変更によるUIの変更ではなく、lintエラーの修正などのソースコードの整形を指します。

## レビュー指摘対応時のcommitメッセージについて
- 指摘対応であることを件名（1行目）に書かない。以下はすべて禁止:
  - 「レビュー指摘対応」「テスト修正」など、変更内容が特定できない件名
  - 「レビュー指摘対応: <内容>」「再レビュー指摘対応: <内容>」のようなラベル付き件名
  - 「レビュー指摘に対応 (must 1件・want 2件)」のような件数だけの件名
  - 件名末尾に「（レビュー指摘対応）」を付ける形式
- 通常のコミットと同様に、変更の性質に応じたプレフィックスを付け、1行目には「何をどう変えたか」を具体的に書く
- 本文（2行目以降）には「なぜ変えたのか」を書く（指摘された問題点や、変更しないと何が起きるか）。軽微な修正なら一言でよい
- レビューコメントのURLが分かる場合は、本文の末尾（Co-Authored-Byトレーラーがある場合はその直前）に `指摘: <コメントURL>` の形式で記載する
- URLが分からない指摘（口頭・Slack等）の場合、指摘元の記載は省略してよい

fix: 🐛 予約作成時のバリデーション漏れを修正

# ブラウザ操作
- 既定では chrome-devtools（ヘッドレス）を使う
- 次の場合は chrome-devtools-headed を使う。自分の判断で切り替えるときは、理由を一言伝える
  - 「ウィンドウを見たい」と言われたとき
  - SSO・二要素認証・CAPTCHA など、人が手で操作する必要があるとき
  - ヘッドレスが原因と疑われる失敗（403、空のページ、広告が出ない）が起きたとき
  - WebGL・canvas・動画・アニメーションなど、描画の見え方を確認するとき

## chrome-devtools-headed のプロファイル競合
- chrome-devtools は `--isolated` 付きで登録してあり、セッションごとに使い捨てのプロファイルで起動する。並列セッションで同時に使っても競合しないが、ログイン状態はセッションをまたいで残らない
- chrome-devtools-headed は、手動でログインした状態を残すために固定のプロファイルで起動する。同じプロファイルの Chrome は同時に1つしか起動できないので、別のセッションが使用中だと `The browser is already running for <パス>. Use --isolated to run multiple browser instances.` で失敗する
- このエラーが出たら、次のことはしない
  - 起動中の Chrome を終了させる（別のセッションが使っている）
  - Playwright などのスクリプトに切り替えて続行する
- 作業を止めて、別のセッションがブラウザを使用中であることを報告し、指示を待つ
